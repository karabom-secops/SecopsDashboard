SecOps Dashboard Architecture

Reflex Solutions · SecOps Dashboard

How the SecOps Dashboard is put together

One Node process serves two audiences that must never see each other's data: Reflex analysts, who see every client, and clients themselves, who see only their own. Everything below is about how that separation is enforced, and where it still depends on someone remembering.

  • Express 4 + PostgreSQL
  • server.js — 5,790 lines
  • 24 lib modules
  • 35 tables
  • 25 browser tab modules
  • no build step

Two surfaces, one process

There is no separate client app. public/portal.html and public/index.html are served by the same Express instance, from the same database, and share a stylesheet — the portal deliberately reuses the dashboard's header, drawer and tab chrome so it reads as one product. What separates them is not deployment. It is a single middleware.

Where it actually runs

One host, one Node process, nginx in front of it. There is no container, no orchestrator, and no process manager in the repository — npm start is node server.js. Everything below is what the code itself asserts about its environment: trust proxy 1, a /secops base path, a Postgres pool, and a data directory it writes to.

This shape is deliberately single-instance. Sessions live in Postgres and would survive a second process, but nothing else would: each instance runs its own timers — double-syncing every integration and duplicating the daily rollups — and each holds part of the report archive and its own copy of data/weeks.json on local disk. Scaling out means moving those two things first, not adding a load balancer.

What a request passes through

Order is the whole design here. Each stage can only protect what runs after it, so the sequence below is the security model — moving any box changes what is exposed.

Why the two APIs resolve tenancy differently

Staff routes accept a tenant as a parameter, because a superadmin legitimately switches between clients all day. Portal routes cannot, for exactly the same reason. The difference is one line of code and the entire threat model.

Where the data comes from

Three ways in, and one thing worth knowing about the way out: the headline numbers are not stored. Secure Score is recomputed on every request from the client's declared estate and its current component scores, so changing an estate figure moves the score immediately and no stale copy survives anywhere to contradict it.

The report pipeline

A board report has three destinations and must be identical in all of them. That is guaranteed by construction: preview, PowerPoint and publish all call the same assembleDeck(), and publishing never re-fetches. If it did, the archived report could differ from the one someone approved, and nobody would ever find out.

server.js holds the routes; the logic that is worth testing has been pulled out beside it. The newest modules were extracted precisely because they needed tests — npm test runs seven suites, no database required.

Sharp edges

A diagram that only shows the intended paths is half a picture. These are real, known, and currently load-bearing on someone remembering them.

  • fails open pageGate admits unmapped prefixes. Any /api route whose first segment is missing from its map is reachable by any signed-in staff user. The membrane is what keeps this from being a client-facing problem — so the membrane must never be reordered or removed.
  • untested No database has been available during development. Every migration and every query has been written and reviewed but never run. For a system whose worst failure is showing one client another's data, a throwaway Postgres with two fake tenants is worth more than any further code review.
  • unrun Several migrations are still pending. Features degrade quietly rather than erroring — the incident phase timeline, for example, simply does not appear until migrate-ir-phase-history.sql is applied.
  • duplicates An escalated event appears twice until an analyst links the IR record to its MDR ticket. Deliberate: fuzzy subject matching would merge unrelated incidents silently, which is worse than a visible duplicate.
  • single point One process, and no supervisor in the repo. If it stops, the site is down and every scheduled sync stops with it — the timers are in-process. Nothing in the repository restarts it, so whatever does that on the host is undocumented here and worth writing down.
  • local state Some state is a file, not a row. The Operations tab is a single global weeks.json — not per-tenant — and published reports are files under data/. Both are on local disk, so a rebuilt host without that directory loses them, and no pg_dump contains them.
  • no csrf Protection is sameSite: strict alone. The portal is read-only so the practical exposure is login CSRF, but an external audience makes this harder to defend in a client security review.
  • config SESSION_SECRET falls back to a literal default. Confirm it is set in the environment before any external user signs in.
